# 需求/功能说明的标准化模板

本文定义「一条功能需求该怎么写」，才能干净地落成一条自然语言用例
（`cases/**/*.yaml`）。目标只有一个：**让需求文档里的每个字段，都能机械地
落到用例的某个字段上，而不是靠读的人“理解”一遍**——理解会丢信息，映射不会。

写用例的完整流程见 [`.claude/skills/nl-case-author/SKILL.md`](../.claude/skills/nl-case-author/SKILL.md)
与 [`.claude/skills/e9-graph-query/SKILL.md`](../.claude/skills/e9-graph-query/SKILL.md)。

## 三条铁律

| # | 铁律 | 违反时怎么办 |
|---|---|---|
| 1 | **验收标准必须描述“用户在屏幕上看见什么”**，不能描述“系统内部做了什么” | 退给产品改 |
| 2 | **一条用例一个操作者**；跨人链路必须拆成“接口前置 + 单人 UI”两段写 | 拆成 `setup:` + `login:` |
| 3 | **每造一条数据都要能说清“谁清、怎么清、失败留什么”** | 没这条就不进回归集 |

第 1 条是根基，它直接决定这个需求是“可测”还是“只能靠人看”。

## 标准模板（十节）

```markdown
## 1. 编号 / 标题
   RF-2026-xxx · <一句话说清做什么>

## 2. 背景与目的
   为什么做。一段话，不参与任何断言。

## 3. 操作者与角色
   - 本 UI 场景的操作者：____________（一个人）
   - 涉及的完整流转链：A 建 → B 会签 → C 审批 → D 归档（若有）

## 4. 前置条件
   - 登录态：____________（哪个账号）
   - 起始页面：____________（URL / 菜单入口）
   - 动手之前环境里必须先存在：____________（流程已到某节点 / 已有某条数据）

## 5. 起始状态
   打开后的地址（能写成 URL 片段就写 URL 片段）

## 6. 操作步骤
   每一步：一个可点元素 + 一句话。例：
   1. 点击「新建流程」
   2. 在流程列表里点击「BYM专用测试」
   3. 在「签字意见」输入框输入「同意流程」
   4. 点击「提交」

## 7. 完成判据（什么时候停）
   例：提交成功后表单页自动关闭、回到新建流程列表页，此时停止。
       表单页还开着的时候不算完成。

## 8. 验收标准（每条必须是下面三种形态之一）
   - URL    ：地址包含 / 等于 ____________
   - 文本   ：页面上能看到 ____________ / 看不到 ____________
   - 元素值 ：元素 ____________ 的值是 ____________

## 9. 数据与清理
   - 造了什么数据：____________
   - 跑完怎么清：____________
   - 失败会留什么、留多久：____________

## 10. 风险与负向
   - 什么“不该发生”（点了没反应 / 重复提交 / 权限外可见）
```

## 字段映射：文档 → YAML

| 模板节 | 落到 YAML | 谁负责 |
|---|---|---|
| 1 编号 | `id` | 机械 |
| 1 标题 | `name` | 机械 |
| 3 操作者 | `login:` | 机械 |
| 4 前置（跨人部分） | `setup:`（走接口备） | 需判断 |
| 4 登录态 | `login:` | 机械 |
| 5 起始状态 | `url:` | 查图谱定 |
| 6 操作步骤 + 7 完成判据 | `goal:` | **翻译，不是抄** |
| 8 验收标准 | `expect:` | 逐条对号 |
| 9 数据清理 | 决定能不能进回归集 | 判断 |
| 10 负向 | `text_not_contains` / `element_absent` | 翻译 |

**第 6+7 是唯一需要“翻译”的地方**——从“操作步骤”翻译成“自然语言意图”：

| 文档里写 | goal 里写 | 为什么 |
|---|---|---|
| `点击 #ecid-29384` | `点击「新建流程」` | ecid 是随机数，下次就变 |
| `点击提交` | `点击「提交」，然后观察页面，表单关闭才算完成` | 不写终点，模型不知道何时 DONE |
| `填写标题` | `在「签字意见」输入框输入「同意流程」` | 点到具体的元素名 |

## 验收标准的“三态”

**每条验收标准必须是下面三种之一，否则退回。**

| 形态 | 模板写法 | YAML |
|---|---|---|
| URL 事实 | 提交后 URL 包含 `/main/workflow/add` | `url_contains` |
| 文本事实 | 页面上显示「新建流程」字样和一条流程名称 | `text_contains` / `ai` |
| 元素值事实 | 「签字意见」输入框的值为「同意流程」 | `element_value` |

**禁止的写法**（这三类在页面上判不出来）：

| ❌ 需求这样写 | 问题 |
|---|---|
| “提交后流程正常流转” | 没有可观测点 |
| “提示信息弹出来了” | 浮层 tooltip **不进页面文本**，断不了 |
| “当前在流转设置页” | “是哪个页面”从正文里判不出来（实测 0.10–0.40） |

对应改法：**把话说成看得见的具体东西**。

```text
❌ “提交后流程正常流转”
✅ “提交后 URL 回到 /main/workflow/add，且页面上不再有「流转设定」这个按钮”
```

> 断言措辞的更多实测口径见 [AGENTS.md](../AGENTS.md)「断言」一节：同一件事，
> 正面陈述能到 0.9+，否定式只有约 0.47，页面身份类最低到 0.10。

## 完整前后对照

### ❌ 原始需求（不可测）

> 用户能在流程模块新建一条流程，填好信息提交后，流程能正常流转，相关人员能看到待办。

### ✅ 标准化后

```markdown
## RF-2026-101 · 新建流程并提交

### 3. 操作者与角色
- UI 场景操作者：employee1（发起人）
- 完整流转链：01 建 → 02/03 会签 → 04/05 审批 → 归档

### 4. 前置条件
- 登录态：employee1
- 起始页面：待办事宜 / 新建流程入口

### 5. 起始状态
{{ base_url }}/wui/index.html#/main/workflow/add

### 6. 操作步骤
1. 点击「新建流程」
2. 在流程列表里点击「BYM专用测试」
3. 在「签字意见」输入框输入「同意流程」
4. 点击「提交」

### 7. 完成判据
提交成功后表单页自动关闭、回到新建流程列表页。
表单页还开着（还能看到「提 交」「流转设定」）时不算完成。

### 8. 验收标准
- 文本：页面上显示「新建流程」字样和一条流程名称
- 文本：页面上看不到「流转设定」
- URL ：地址包含 /main/workflow/add

### 9. 数据与清理
- 造了：一条「BYM专用测试」流程实例（{{ wf_request_name }}）
- 清理：跑完推归档，只认 jev-wf_ 与「路径名-登录名-日期」两种标题

### 10. 风险与负向
- 不填内容直接提交，不应产生新流程（→ 单独一条负向用例）
```

这份标准化的需求，**可以一字不差地落成 YAML**：第 6、7 节拼成 `goal`，第 8 节拆成
3 条 `expect`，第 3 节给 `login`，第 9 节回答“能不能进回归集”。

## 需求评审清单

收到需求，过这张表；任何一条打不上钩就标记为“待澄清”，不硬写：

```text
□ 1. 操作者是谁，一个人还是一串人（跨人是否已拆成接口前置）
□ 2. 起始页面有 URL 或能查到路由
□ 3. 每步操作都点到了具体元素名，没有 id/坐标/函数名
□ 4. 完成判据写清了“什么时候停”
□ 5. 每条验收标准都是 URL/文本/元素值 三态之一
□ 6. 每条验收标准回答的是“屏幕上看见什么”，不是“系统做了什么”
□ 7. 造了什么数据、谁清、失败留什么
□ 8. 有哪些“不该发生”（负向）
```
